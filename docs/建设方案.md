## 总体技术底座（各版本共用，一次说清）

### 代码仓库结构

```text
liuquan/
├── engine/                  AI 引擎（L2，独立可测，无业务概念）
│   ├── core/                状态机 / Policy 门禁 / 检查点 / 审计 / 队列消费
│   ├── registry/            工序与链的 YAML 声明 + schema 校验 + loader（拒载）
│   └── workers/             AI 工序实现（<域>/<工序>/run.py + schema.py + config/）
├── models/                  Pydantic Model：工序输出契约 + 四契约（Event/Context/Action/Task）
├── web/                     业务应用（L1，FastAPI + Jinja2 + HTMX）
│   ├── tm/ crm/ erp/ seo/ scrape/
│   ├── engineapi/           引擎对外三接口
│   └── templates/ static/
├── migrations/              Alembic（业务库 + 引擎库两套）
├── tests/                   单测（fake LLM）+ 端到端
├── scripts/                 部署 / 数据迁移 / 运维脚本
├── deploy/                  systemd 单元 + 部署说明
└── docs/                    文档（本目录）
```

### 数据库（PG16 单实例双 database）

```text
业务库 liuquan：          schema: crm / tm / erp / seo / scrape
引擎库 liuquan_engine：   引擎任务 / 步骤 / 检查点 / 审计 / 配额 / 调度表
外部只读：                NocoBase PG 的 v_* 视图（只读账号连接）
```

### 引擎任务运行模型（贯穿所有版本）

```text
触发（人工API/事件/定时）
  -> scheduler 建 engine_task（含链定义）入队
  -> runner 消费（SELECT ... FOR UPDATE SKIP LOCKED）
  -> 每工序跑状态机：INIT -> REASON(AI) -> ACT -> OBSERVE -> VERIFY -> 终态
  -> 每相位转换前写 checkpoint；每次 LLM 调用写 audit
  -> 链完成：产出 TaskProposal / 分析结果，通知 TM
```

### 四契约（Business AI Contract，业务模块接入引擎的唯一接口）

| 契约 | 方向 | 含义 | 例子 |
|---|---|---|---|
| Event | 业务 -> 引擎 | "我发生了什么" | 库存低于阈值、收到新消息 |
| Context | 业务 -> 引擎 | "我能给你看什么"（数据供给声明） | 该 SKU 近 30 天销量/现库存/交期 |
| Action | 引擎 -> 业务 | "你可以建议我做什么"（引擎声明产出类型） | 创建采购任务、生成翻译 |
| Task | 引擎 -> TM | "帮我派活给人" | 一条带来源追溯的任务提案 |

新业务模块接入 = 在 `models/contract/` 登记这四样 + 工序声明。引擎代码零改动。⚑ 四契约的字段级规范是 v0.1 详设的第一项。

## v0.1 引擎地基

**做什么**：引擎最小内核，命令行可跑通一个工序，全程可审计可恢复。

### 实现内容

| # | 内容 | 说明 |
|---|---|---|
| 1 | 状态机 | 5 相位（INIT/REASON/ACT/OBSERVE/VERIFY + 终态 DONE/FAILED/PAUSED）；相位转换代码写死；每工序一次状态机实例 |
| 2 | PydanticAI 接入 | `output_type` 即输出契约；模型实例走配置（`text -> deepseek-chat`）；重试/超时/降级策略 ⚑ |
| 3 | 工序注册表 | `engine/registry/`：工序 YAML（id/domain/inputs/outputs/model/风险/version）+ 链 YAML（工序序列）；loader 全册 schema 校验，缺字段拒载启动失败 |
| 4 | 审计 | 每次 LLM 调用记录：输入摘要/输出/token 数/耗时/耗时毫秒/模型/工序/任务 id，落引擎库 |
| 5 | 检查点 | 每相位转换前落库；崩溃后重启从最后检查点续跑（不重烧 token） |
| 6 | 队列消费（雏形） | `engine_task` 表 + SKIP LOCKED 取任务；本版仅命令行触发入队 |
| 7 | 演示工序 | 1 个端到端工序（建议：echo-结构化，输入文本输出固定 Model）+ 1 个真调 DeepSeek 的工序（建议：翻译雏形，为 v0.3 探路） |
| 8 | CLI | `liuquan-engine run <task>` / `resume <task>` / `verify` / `registry-check` |
| 9 | lint 工具 | `engine/lint` 三规则（P1 业务词黑名单-词表从注册表自动生成 / P2 凭据端点零容忍 / P3 契约），每规则配反向测试；挂入 verify 成为四绿之一（规范 R10 四层防线的机器层） |

### 怎么做（关键设计）

- 引擎不依赖 web，可独立进程运行；对 DeepSeek 的调用只在 `engine/core/llm` 一处
- 硬编码四层防线在本版立住（承广成 2026-08-18 审计返工的教训）：架构层（工序只碰 inputs/config/原语）从第一行代码就守；lint 工具与首批工序同步落地，不事后补；演示工序的规格值全部走 config/，作为外置范例
- 单测 fake LLM：stub PydanticAI Agent 类，断言 prompt 组装与输出类型校验路径；不依赖网络（规范 R12）
- 反向测试：注册表缺字段拒载、绕过注册表直调工序函数被拒、模型 id 内联进 run.py 被 lint 拦
- 审计内容脱敏：对话全文不进日志，进审计表（受控可查），日志只留摘要 ⚑ 规则详设定

### 做完是什么样子

```bash
$ liuquan-engine run "translate" --input '{"text":"hello"}"
task e-001 created, chain: translate
  [INIT]    policy ok (domain=demo, risk=read)
  [REASON]  pydantic-ai -> deepseek-chat, 320 tokens, 1.2s
  [ACT]     write result
  [VERIFY]  fields ok
  [DONE]    1.4s total
$ liuquan-engine audit e-001        # 查输入输出/token/耗时
```

### 验收标准

- [ ] 命令行提交工序任务，状态机全相位走完到 DONE
- [ ] 注册表缺字段，引擎拒启动（有反向测试）
- [ ] 审计表可查：每次调用的输入/输出/token/耗时
- [ ] REASON 中途 kill 进程，重启后从检查点续跑，前段 AI 结果不重烧
- [ ] 全量单测绿（fake LLM，零网络依赖）
- [ ] lint 三规则生效：故意违规样本（业务词/密钥/直连 SQL）各被拦截（反向测试覆盖）
- [ ] 换模型只改配置文件不改代码（测试覆盖）

## v0.2 TM + 引擎接通

**做什么**：AI 建议自动变任务，人工处理完回流；Web 骨架立起来。

### 实现内容

| # | 内容 | 说明 |
|---|---|---|
| 1 | 双 database | 业务库 liuquan（tm schema 先行）+ 引擎库；Alembic 两套迁移 |
| 2 | 队列完整化 | runner 常驻进程消费 engine_task；并发上限；失败重试策略 ⚑ |
| 3 | TM 数据模型 | task（目标/负责人/截止/状态/来源追溯）、task_proposal（AI 提案 + 风险级）、task_event（状态流水）。**细则已拍板（2026-08-27，2026-08-28 修订：取消 P0-P3 优先级分级**——无分级标准、AI 分级不准确、人工难界定，逾期标红保留、「逾期自动升级」随分级取消；后续有标准则 AI 按标准分级再议**）**：负责人按角色（运营/采购/管理员）指派，AI 提案按工序域带默认角色可改；截止手填 + AI 建议可改；状态五态 open/in_progress/done/void/blocked（blocked=等物料/等回复）；循环任务不在 TM 做，统一交 v0.4 定时链。**任务生成细则（决策 16，2026-08-28：任务生成双通道（AI 生成 + 人工输入）；任务来源 = 业务系统（CRM/ERP/SEO 等）+ 任务系统自身，task.domain 标来源域（列表标来源徽章）；AI 提案审核依据强制展示（每条 evidence 类型+ref_id+原文摘录+查看入口），AI 可引用数据受链白名单封闭，100% 禁止幻觉（机器校验拒落））。任务生命周期细则（决策 17，2026-08-28：两种结束方式（完成/作废）都必须人工回复，不回复不能结束；派生新任务不代表原任务结束；权限 v0.2 不做、将来必须引入完善权限系统（精确到人和数据，同页面不同人看到不同任务数量与内容），架构留位；同事件防重（同业务对象+同建议类型，未完成任务一直挂着不自动清理）；任务生成后有权限人员可编辑；逾期一直提醒 + 列表筛选（筛选条件后定，一定有））** |
| 4 | TaskProposal 审核流 | **全部提案进审核页人工批/驳**（2026-08-27 业务拍板，不设代码自动通过）；风险级仍由代码规则标注（域 + 动作类型查表），作展示与排序用；**审核页强制展示提案依据（evidence 类型+ref_id+原文摘录 + 查看入口 + 审计兜底）**（决策 16） |
| 5 | FastAPI 骨架 | 路由骨架 + Jinja2 模板基座 + 共享密码登录 + 三角色标签（管理员/运营/采购） |
| 6 | 引擎三接口 | POST /api/engine/tasks、GET /api/engine/tasks/{id}、GET /api/engine/registry |
| 7 | 状态回流 | 任务完成后结果事件回引擎（为 v0.4 事件触发的闭环留位） |
| 8 | 演示链 | 一条"工序链 -> 提案 -> 任务 -> 处理 -> 回流"的端到端演示链 |
| 9 | 工作台 | 一级菜单，**当前版本无内容**（统计等内容后续在定；决策 15：统计数据一定会做，方向确认后按需纳入后续版本） |

### 怎么做（关键设计）

- web 只经三接口碰引擎，不 import engine 内部模块（规范 R4 的工程边界）
- 提案风险判定是**代码规则**（域 + 动作类型查表），不是 AI 自评（规范 R5）
- 登录从简：共享密码 + 角色 cookie；会话过期/角色权限点后续版本按需加

### 做完是什么样子

浏览器打开 `http://<host>:<port>` 登录 -> 首页是任务清单页 -> 触发演示链 -> 提案出现在"待审核"栏（附提案详情与来源）-> 人工批准后入清单（标"AI 建议"来源）-> 勾选完成 -> 任务事件落库，引擎可见。

### 验收标准

- [ ] 触发工序链 -> 产出提案 -> 全部进审核页 -> 人工批准后成任务
- [ ] 人工处理任务 -> 状态回流，引擎可查
- [ ] 三接口可用（curl 可演示）
- [ ] 登录与角色标签生效
- [ ] runner 崩溃自动重启（systemd）后队列不丢任务
- [ ] 全量单测 + 四绿

## v0.3 CRM 平移

**做什么**：EOMS 已验证的 CRM 链路在刘全跑通，体验不倒退（基线 5.8s），广成电脑关机不影响。

### 实现内容

| # | 内容 | 说明 |
|---|---|---|
| 1 | 四工序平移 | chat-translate / snapshot-update / todo-generate / customer-reply-draft；逻辑参考广成同名 SKILL，调用层换 PydanticAI（删手写 normalize） |
| 2 | 风格指南配置 | 承接广成 customer-chat-extract / customer-reply-draft 的 config/（风格指南/术语表），改配置不改代码 |
| 3 | crm schema | customer / message / snapshot / todo_candidate；滚动快照机制平移 |
| 4 | CRM 页面 | 粘贴对话页（触发链）、翻译+快照展示、回复台（auto/points/literal 三模式）、待办确认入库 |
| 5 | EOMS 数据迁移 | EOMS SQLite -> 刘全 PG crm schema 脚本（存量：4 客户/9 消息/1 待办，量极小）；幂等可重跑 |
| 6 | 飞书通知 | 任务生成/待审核提醒走飞书 webhook 卡片（承接 EOMS 现有通道） |
| 7 | 异步化改造 | 页面提交即返回任务 id，轮询/SSE 显示进度，取代 EOMS 的 300s 同步阻塞 |

### 怎么做（关键设计）

- 链定义：`chat-translate -> snapshot-update -> todo-generate`（回复台按需单独触发单工序链）
- 每工序一个 output Model（ChatTranslateResult 等），字段对齐广成交付物结构，减少迁移摩擦
- 端到端耗时目标 <= 6s：翻译/快照/待办三工序串行 DeepSeek 调用，预估 3-5s；超标的优化手段（并行化/上下文裁剪）预留 ⚑
- 迁移脚本入 `scripts/`，跑前备份、跑后对账（条数校验）

### 做完是什么样子

员工在 CRM 页粘贴一段英文对话 -> 点"翻译" -> 2 秒内开始逐条出译文 -> 快照更新 -> 待办候选列出（带依据引用）-> 确认入库 -> 待办出现在 TM 清单（标来源 CRM）-> 飞书收到提醒。

### 验收标准

- [ ] 粘贴对话全链路自动跑完，端到端 <= 6s
- [ ] 待办出现在 TM 清单（标来源）
- [ ] 存量 4 客户/9 消息/1 待办完整迁入，对账通过
- [ ] 断网/DeepSeek 故障时页面显示可理解的失败态，不白屏不挂死
- [ ] 广成电脑关机，全链路正常（链路全程云上）
- [ ] 审计可查每次翻译的 token/耗时

## v0.4 调度完整版

**做什么**：无人工干预，系统自己发现事、生成任务。

### 实现内容

| # | 内容 | 说明 |
|---|---|---|
| 1 | 事件触发 | event_subscription 表（事件类型 -> 链）；业务模块发 Event 入队；去重（同事件 N 分钟内不重复触发）|
| 2 | 定时触发 | schedule 表（cron 表达式 -> 链）；systemd timer 或引擎内调度器 ⚑ 详设定 |
| 3 | 首批定时链 | CRM 未跟进提醒（超 N 天无跟进的客户）⚑；清单需业务拍板 |
| 4 | 配额记账 | quota_ledger：外部 API（eHunt 200 条/天）统一记账；超限工序排队次日跑，不报错 |
| 5 | 限流 | 引擎任务并发上限 + 每工序 QoS ⚑ |

### 做完是什么样子

每天早上 7 点（⚑ 待拍板）系统自动跑 CRM 未跟进检查 -> 3 个超过 5 天没跟进的客户 -> 提醒任务已在 TM 清单 -> 飞书早报卡片。同一客户当天重复触发只生成一次。

### 验收标准

- [ ] 定时任务每天自动跑，任务就位在 TM
- [ ] 同事件重复触发被去重（测试覆盖）
- [ ] eHunt 配额超限时工序挂起排队而非报错
- [ ] 调度器崩溃重启后不漏跑/不重跑（幂等）

## v0.6 ERP 增强

**做什么**：库存与订单事实进刘全视角（只读）。

### 实现内容

| # | 内容 | 说明 |
|---|---|---|
| 1 | 视图接入 | 只读账号连 NocoBase PG，读 25 个 v_* 契约视图；ERP 域 Context 数据供给声明 |
| 2 | 补货建议工序 | 输入：SKU 近 30 天销量/现库存/供应商交期（来自视图）；输出：补货建议 Model -> 提案 |
| 3 | 备货缺口分析工序 | 套装 BOM vs 在途 vs 现货（数据来自三工作台三层模型）⚑ |
| 4 | 异常订单预警工序 | 规则检测（超期未发/地址异常）+ AI 归因说明 |
| 5 | 库存体检定时链 | 每日：读视图 -> 缺口检测 -> 建议工序 -> 补货任务进 TM |

### 怎么做（关键设计）

- **对 NocoBase 物理只读**：连接用只读账号；代码层再拦写 SQL（规范 R18 双保险，反向测试覆盖）

- 视图层封装为 ERP 域 Context provider，未来 ERP 重构换数据源只改 provider，工序链不动

### 验收标准

- [ ] 库存体检发现低库存 -> 补货任务进 TM（附销量/库存/交期上下文）
- [ ] 全程对 NocoBase 零写入（反向测试 + 只读账号双验）
