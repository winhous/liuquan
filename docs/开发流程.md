# 刘全开发流程

> 本文回答一个问题：**怎么确保 AI 开发时强制按照文档目标与规范执行**。
> 它是强制机制的宪法：三层防线（知道 -> 难违规 -> 违规过不去），六项设置。
> 与 `开发规范.md` 的分工：规范管"代码长什么样才合规"（R1-R25），本文管"开发过程怎么被卡住"（流程闸门）。

## 强制哲学

AI 不守规范的失效模式有三种，对应三层手段：

```text
第 1 层  让 AI 知道规范    （CLAUDE.md 入口卡 / 会话启动读文档）     -- 引导
第 2 层  让 AI 难以违规    （详设先行 / 逐任务执行 / 变更日志卡点）   -- 流程
第 3 层  让违规过不去      （五绿 hook / 验收断言 / 审计）           -- 机器
```

**第 3 层是唯一真正的强制**--与 AI 自觉与否无关，脚本不绿提交都过不去。
与刘全系统自身的哲学同构：**AI 可以开发，脚本负责验收。**

## 六项设置

### ① CLAUDE.md 入口卡（第 1 层，已在位并加强）

- CLAUDE.md 每次会话自动加载，是唯一保证进上下文的文件
- 最关键的规矩**内联在 CLAUDE.md**（不是指针）：五绿、变更日志、安全红线、详设先行
- 指针文档（开发规范全文）供深读，但入口卡保证 AI 至少看到红线级条目

### ② 详设先行卡（第 2 层）

```text
每个版本开工前：详设文档（表结构/schema/prompt 草案）→ 用户确认 → 才写代码
没有确认的详设不动代码（文档先行，规范既有规矩的流程化）
```

- 详设文档放 `docs/`，命名 `详设-v0.x-<主题>.md`
- 详设确认是**业务/技术双确认**：业务字段用户拍板，技术细节技术方定（已授权）
- 开发中发现详设有误：先改详设再改代码，变更日志留痕

### ③ 逐任务执行卡（第 2 层）

版本拆成小任务（每个任务 = 一个可验证单元：代码 + 测试 + 文档同步），节奏：

```text
任务清单（开工时从详设拆出）
  → 每任务：TDD（先测试后实现）→ 五绿 → 变更日志 → commit
  → 任务完成勾掉，下一任务
禁止：跳任务、跨任务批量提交、"先写完再补测试"
```

- 用 superpowers 的 writing-plans / executing-plans / TDD skill 辅助（环境已装）
- 每任务一个 commit，commit message 说清做什么；禁止巨型混合提交

### ④ 五绿 hook（第 3 层，v0.1 第一批代码）

`scripts/check.sh`（v0.1 与首批工序同步落地）：

```bash
check.sh = engine/lint（P1/P2/P3 三规则）
         + registry 一致性校验
         + 全量单测（fake LLM）
         + verify
         + 断言覆盖检查（scripts/check_acceptance.py + tests/acceptance_manifest.yaml）
```

挂 **git pre-commit hook**：不绿不让提交。配 `--no-verify` 豁免需人工记录原因（变更日志留痕，审计可查谁绕过）。

### ⑤ 验收断言卡（第 3 层）

- 建设方案每版的验收标准，全部写成**可执行测试**（进 tests/，标记 `@version_acceptance.v0_x`）
- 版本完成定义 = 验收断言全绿 + 用户复核确认，两者缺一不可
- AI 无法"自称完成"：跑 `pytest -m version_acceptance` 见真章

**断言覆盖机器检查（B1，2026-09-03）：** `tests/acceptance_manifest.yaml` 是断言单一事实源（版本 → 断言编号 → 测试函数名 → 验收描述），`check.sh` 第 5 门校验 manifest 与实际测试函数的一致性。pytest 绿 ≠ 断言覆盖绿：A47/A48/A51 无测试时 `64 passed` 依然全绿——只有 manifest + 检查器才能暴露「断言无测试」假绿。

### ⑥ 发版前审计（第 3 层，兜底）

- 每版发版（git tag）前跑一次合规审计：文档与代码一致性、变更日志完整性、红线抽查（Etsy 写/NocoBase 写/密钥入 git）
- v0.1-v0.5 人工审（对话式审计，报告落 `docs/审计-<版本>-<日期>.md`）；v0.6 起尽量脚本化进 check.sh
- 审计发现红项：先修再发版，禁止红着发版（规范 R13）

### 主代理验收执行卡（B3，2026-09-03）

每批验收流程（子代理交付后主代理必须执行）：

1. **跑五绿**（含第 5 门断言覆盖）：`bash scripts/check.sh` 全部五门通过，任一红 = 本批不通过
2. **逐条核对详设断言表 vs manifest vs 测试函数 vs 实现（四方对账）**：详设 §11 断言表每个 A 编号，逐条检查——manifest 有登记 + manifest 指向的测试函数真实存在 + 测试函数内有对实现的实质断言（非空壳）
3. **核对结果进变更日志**：每批验收结果（通过/打回 + 问题清单）追加到 `docs/变更日志.md`
4. **发现断言无测试 = 红**：先补测试再进下一批，不得跳过

**对账表格模板：**

| 断言号 | 详设声明 | manifest 状态 | 测试函数 | 实现核对 |
|---|---|---|---|---|
| A46 | 导航改造：SEO 下二级含扒图 | implemented | test_a46_nav_seo_children_scrape_first | ✅ |
| A47 | 丢链接进扒图→image_file 落库 | planned（B5 补） | — | 待补 |
| ... | ... | ... | ... | ... |

### 子代理交付约束（B4，2026-09-03）

开发 prompt 硬性要求（主代理派发子代理时必须包含）：

1. **断言映射**：每条断言必须给出「断言编号 → 测试函数名」映射，写入交付报告
2. **自报通过必须附证据**：测试函数名 + 测试运行结果（passed 数 + 具体输出），无测试不得声称通过（铁律 7 机器化）
3. **交付物必须含三项**：「涉及断言清单 + 对应测试函数 + 测试运行结果」，缺一项 = 验收不通过打回
4. **禁止假绿**：子代理不得在无测试函数的情况下报告断言通过；`grep -c "test_aXX" tests/` 为 0 即判定虚报

## 开发节奏总览

```text
【版本级】详设 → 用户确认 → 任务拆解 → 逐任务（TDD+五绿+日志+commit）→ 验收断言全绿 → 用户复核 → 审计 → git tag
【任务级】读详设与相关规范 → 写测试 → 实现 → 五绿 → 变更日志 → commit
【会话级】启动读 CLAUDE.md + 项目状态.md → 弄清当前版本/任务 → 干活
```

## 责任分工

| 事项 | 谁定 |
|---|---|
| 业务字段/优先级/范围 | 用户拍板 |
| 技术细节/表结构/schema | 技术方定（已授权），详设文档留痕 |
| 合规与否 | 机器（五绿/断言/审计），不由人也不由 AI 自评 |

## 例外与豁免

- 任何卡点的豁免（跳五绿/跳详设）必须：用户明确同意 + 变更日志留痕（谁、何时、为何）
- 没有留痕的豁免按违规处理（审计追溯）
