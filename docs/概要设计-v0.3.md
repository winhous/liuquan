# 1. 项目背景与目标

## 1.1 业务背景

当前业务资产（2026-08 摸排结论）：

| 资产 | 状态 | 在新系统中的角色 |
|---|---|---|
| EOMS（刘全初版，阿里云） | 生产运行，但 AI 依赖本地广成电脑开机 | **退役**，数据迁移，链路平移 |
| Studio（广成，本地） | 引擎成熟（444 单测全绿），但无网关无常驻，内容创作域包袱重 | **退出刘全生产链路**，只继承其机制设计（取骨弃肉） |
| NocoBase ERP（阿里云，PG16） | 生产运行，订单/物料/库存/结算/物流全在此 | **不动**，刘全一期只读其数据契约视图；重构为挂起议题 |
| AWS Etsy 拉取链路 | 生产运行（7 店 token，防封店生存约束） | **一根线不动** |
| 飞书 | 通知通道（webhook 卡片） | 保留通知职能 |

## 1.2 目标

做一个替团队管理 Etsy 小店日常运营的 **AI 大管家系统**：

> 它盯着店铺的生意事实（订单、库存、客户、流量），主动判断"现在最该做什么事"，把该做的事变成任务派给团队里的人，人做完之后它再接着判断下一步，如此循环。

三个组成部分：

1. **一套业务账本**（CRM / SEO / ERP 视图）：真实发生的业务事实，各归各的系统记录管理。AI 不碰最终数据。
2. **一个 AI 大脑**（AI 引擎）：干非确定性的活--理解对话、分析数据、判断该做什么、生成建议。AI 提建议，不直接改账本。
3. **一个派活的工头**（TM 任务中心）：AI 的判断全部变成任务，人执行，结果回流，AI 判断下一步。

## 1.3 与初版（EOMS）的本质区别

初版是三个工具（翻译 CRM + SEO 生成器 + 手写待办），工具之间没有循环。刘全 v2 要的是循环：

```text
业务事实 -> AI 理解并判断 -> TM 形成任务 -> 人执行 -> 结果回流 -> 下一轮判断
```

且初版的生产架构缺陷（AI 可用性依赖一台本地电脑开机）在新系统中彻底消灭。

# 2. 总体设计原则

## 2.1 AI 引擎：取广成之骨，换 PydanticAI 之心（核心决策）

**新建刘全 AI 引擎**，全新代码库，不 import 广成任何模块，不背广成 28 个存量工序。设计上继承两边精华：

**继承自广成（骨）--机制层：**

| 机制 | 广成中的原型 | 刘全版 |
|---|---|---|
| 状态机驱动 | 5 相位（NEW_TASK->REASON->ACT->OBSERVE->VERIFY->DONE） | 每个引擎任务 = 一个状态机实例 |
| 相位门禁 Policy | PolicyEngine 80 行，按相位限读写 | 按业务域的权限矩阵 + 动作风险分级 |
| 检查点持久化 | checkpoint JSON 落盘（薄实现） | PG 落盘，崩溃恢复、断点续跑 |
| 暂停/人工审批恢复 | 已实现且真实跑通 | 引擎任务可 PAUSED，人工恢复 |
| 事件审计日志 | event_log JSONL 每步落盘 | 每次调用记输入/输出/token/耗时/成本 |
| 工序契约 | run(inputs, engine) -> dict | 工序输出必须是 Pydantic Model |
| 声明式注册表 | YAML + schema 校验，不合规拒载 | 同样纪律，按刘全业务域重组 |
| 测试守门 | 444 单测 + registry 一致性 + lint 四绿 | 同样纪律，作为发版门槛 |

**继承自 PydanticAI（心）--调用层：**

| 能力 | 广成的缺口（代码实证） | PydanticAI 提供 |
|---|---|---|
| 输出格式强制 | prompt 里"嘴上说"输出 JSON，无机器强制 | output_type 即契约，类型校验不过就是不过 |
| 校验失败自动重问 | chat_json 解析失败直接 return None，工序判 failed | 自动带错误信息 re-ask，模型自己修正 |
| 字段级容错 | 60+ 行手写 \_normalize\_* 函数 | 类型定义即校验器，直接删掉 |
| 换模型 | 5 层环境变量 fallback + key 格式嗅探补丁 | 字符串换模型（deepseek:deepseek-chat） |
| 用量观测 | 只有 last_error 一个字符串 | token/耗时记录 |

**刘全新增（两边都没有）：**

- 事件/定时/人工三路触发调度（广成是拉模式无调度）
- 异步任务队列（取代 EOMS 同步阻塞 300s subprocess）
- 按业务域的上下文隔离（crm 工序只能读 crm 域，越域需显式声明+审批）
- 外部配额记账（eHunt 200 条/天等统一管理）

## 2.2 Code + AI 双轨

代码负责确定性问题：数据一致性、状态机、权限、业务事务、金额计算、最终状态转换。
AI 负责非确定性问题：理解、提取、分类、总结、推理、建议、规划、下一步判断。

> **AI 可以提出，代码负责验证；AI 可以判断，业务系统负责最终执行。**

「AI 100% 可控」的工程含义：AI 永远只在 REASON 相位（及 ACT 的内容生成环节）出现；输出必过三层校验（PydanticAI 类型校验 -> 业务规则代码校验 -> 审计抽查）；所有状态转换代码写死；AI 无法决定下一步、无法直接写业务库、无法越域访问。

## 2.3 业务与 AI 解耦

业务模块无 LLM 依赖。与引擎的全部交互走统一契约：

```text
Event    （我发生了什么）     -- "库存低于阈值"
Context  （我能给你看什么）   -- "该 SKU 近 30 天销量、现库存、供应商交期"
Action   （你可以建议我做什么）-- "创建采购任务"
Task     （帮我派活给人类）   -- "审阅这条 SEO 建议"
```

新业务模块接入 = 登记这四样东西，引擎零改动。这是 4 块业务扩到 8 块的扩展机制。

## 2.4 模块化扩展，但组合权收归系统

不做「任意工作流随意组合」的平台（广成的平台野心降级），不做自主 Agent。工序链预定义（蓝图），组合定义权在系统设计者。

# 3. 总体架构

## 3.1 四层结构

```text
┌─────────────────────────────────────────────────────────────┐
│  L1 业务应用层（团队每天用的页面和账本）                       │
│   TM 任务中心 │ CRM │ ERP(只读增强) │ SEO │ 扒图工作台        │
└──────────────────────────┬──────────────────────────────────┘
                           │ 统一契约：Event / Context / Action / Task
┌──────────────────────────▼──────────────────────────────────┐
│  L2 AI 引擎层（liuquan-engine，新建）                         │
│   调度器（事件/定时/人工三路触发）                            │
│   执行器（状态机实例）· Policy 门禁 · 检查点 · 审计           │
│   工序注册表（YAML 声明 + schema 校验）                       │
└──────────────────────────┬──────────────────────────────────┘
                           │ PydanticAI
┌──────────────────────────▼──────────────────────────────────┐
│  L3 模型层（DeepSeek / 未来多模型，字符串切换）               │
└─────────────────────────────────────────────────────────────┘
                           ▲
┌──────────────────────────┴──────────────────────────────────┐
│  L0 数据层（PG16 单实例双 database）                          │
│   业务库（crm/tm/erp/seo schema）+ 引擎库（隔离）             │
│   + 外部只读：NocoBase PG 的 v_* 契约视图                     │
└─────────────────────────────────────────────────────────────┘
```

## 3.2 AI 引擎五部件

1. **调度器 Scheduler**：事件订阅表 + 定时表 + 人工入口 API + 去重限流。触发即创建「引擎任务」（一条预定义工序链）落库进队列。
2. **执行器 Runner**：取出任务，创建状态机实例，逐工序执行（INIT->REASON->ACT->OBSERVE->VERIFY 循环，DONE/FAILED/PAUSED 终态）。
3. **Policy 门禁**：域权限矩阵（工序声明所属域，只能读该域上下文）+ 动作风险分级（只读 < 建议 < 写业务数据 < 执行事务，级越高审批越重）。
4. **检查点 Checkpoint**：每状态转换前落盘；PAUSED 可人工恢复；崩溃后从最后检查点续跑不重烧 token。
5. **审计 Audit**：每次 LLM 调用的输入/输出/token/耗时/成本全量落盘，按任务/按工序/按天可查。

另有**工序注册表**：每个 AI 工序一个声明（域/输入输出类型/模型/重试策略/风险等级），YAML 登记，schema 校验不合规拒载。

## 3.3 引擎对外接口（一期仅三个）

```text
POST /api/engine/tasks          人工触发一个工序链
GET  /api/engine/tasks/{id}     查状态/结果/审计
GET  /api/engine/registry       工序/链清单（管理页用）
```

事件与定时触发由引擎内部订阅表驱动，不对外。

## 3.4 一次引擎任务的生命周期（示例：CRM 翻译链）

```text
1. 人工触发：员工在 CRM 页粘贴对话点「翻译」
2. 调度器建引擎任务（链：chat-translate -> snapshot-update -> todo-generate）
   落库进队列
3. 执行器逐工序跑状态机：
   chat-translate:
     INIT    Policy 校验（crm 域，输出类型 ChatTranslateResult）
     REASON  组上下文 -> PydanticAI 调 DeepSeek -> 类型校验
     ACT     译文写 crm 库
     VERIFY  代码验证（条数对得上原文？译文非空？）
   snapshot-update: 同上循环
   todo-generate:   产出待办候选 -> 生成 TaskProposal（不直接写库）
4. 链完成 -> TM 收到任务提案 -> 审核（全部提案人工批/驳）
5. 全程每步落审计与检查点
```

# 4. 业务模块设计（一期）

## 4.1 TM 任务中心（人机协作核心出口）

- 任务一等公民：目标、负责人、优先级、截止时间、状态、执行结果、来源追溯（哪个 AI 任务/哪次人工操作产生的）
- 任务来源：人工创建、AI 提案（TaskProposal，**全部进审核页人工批/驳**，不设代码自动通过）、任务完成后自动生成的后续任务
- 跨域统一清单：CRM 跟进、SEO 优化、采购补货、选品建议混排，标来源
- **验收形态**：团队每天打开刘全，看到的是按优先级排好的任务清单和生意总览，而不是一堆工具

## 4.2 CRM（第一个真实业务）

- 平移 EOMS 已验证链路：粘贴对话 -> 翻译 -> 滚动快照 -> 回复台（三模式）-> AI 待办
- 改造点：链路从「同步 subprocess 调广成」改为「走刘全引擎异步」；数据从 EOMS SQLite 迁入刘全 PG crm schema（存量：4 客户/9 消息/1 待办，量极小）
- 体验基线：EOMS 端到端 5.8 秒，新系统不倒退

## 4.3 ERP 模块（只读增强层；重构挂起）

> 业务拍板：ERP 大概率重构，但时机未定，一期不动 NocoBase。

一期做法：
- **数据视图层**：读 NocoBase PG 的 25 个 v_\* 契约视图（订单/库存/物料/结算，现成且稳定）
- **AI 增强层**：补货建议、备货缺口分析、异常订单预警等工序，产出任务进 TM
- **预留接入位**：数据契约按视图读，未来 ERP 重构时切换数据源即可，工序链不动

红线（继承三机架构）：刘全不做任何对 Etsy 的写操作（上架/改价延续人工 + 任务单模式）。

## 4.4 SEO

- 平移已验证工序：keyword-research（eHunt 数据）、seo-optimize（标题/标签/描述优化）
- 新增定时链：每日/每周 listing 体检（排名与关键词数据 -> 变化检测 -> 优化建议任务）
- eHunt 配额（200 条/天）进引擎统一记账

## 4.5 扒图工作台

- 平移 image-download 工序（闲鱼/小红书扒图）
- 新链：扒图 -> 图片体检（分辨率/水印）-> 选品建议 -> TM 选品任务
- 对接三工作台方案 v3 的选品工作台流程（选品卡/查重/建档派发链路在 NocoBase 侧，刘全负责扒图与建议环节）

## 4.6 AI 引擎

见第 3 节。一期完成最小内核：状态机 + PydanticAI + 审计 + 人工触发 + 基本调度；事件/定时触发在第 4 步补齐。

# 5. 基座设计

## 5.1 部署形态

```text
现状（不动）：
  AWS（34.228.44.95）    拉 Etsy 数据（7 店 token），唯一平台出口
  阿里云（112.124.33.142）NocoBase ERP + 数据落库
  本机/办公机             开发

新增（阿里云上，与 NocoBase 同机）：
  刘全 Web（FastAPI 常驻，团队浏览器访问）
  AI 引擎（常驻进程：调度+执行+审计）
  PG16（刘全业务库 + 引擎库，双 database 隔离）
```

- 刘全 v2 取代 EOMS；广成本地退出刘全生产链路
- 引擎在云上常驻，**广成电脑关机不再影响任何功能**

## 5.2 技术栈（全免费开源）

| 部件 | 选型 |
|---|---|
| Web 后端 | FastAPI + SQLAlchemy 2.0（EOMS 已验证） |
| 前端 | Jinja2 + HTMX（页面原型阶段可再评估） |
| 数据库 | PostgreSQL 16（业务库 + 引擎库） |
| AI 调用 | PydanticAI + DeepSeek |
| 队列 | PG 内置队列（SKIP LOCKED），规模大再议 |
| 常驻 | systemd 服务 |

## 5.3 数据布局

```text
业务库 liuquan：
  schema: crm / tm / erp(分析结果) / seo
引擎库 liuquan_engine（独立 database，物理隔离）：
  引擎任务、检查点、审计、配额记账
外部只读：
  NocoBase PG 的 v_* 视图（ERP 事实数据）
```

## 5.4 用户与权限（一期从简）

共享密码登录 + 三角色标签：管理员（全部权限 + 引擎管理页）/ 运营 / 采购。权限模型可扩展，不做复杂 RBAC。

## 5.5 现有系统处置总表

| 系统 | 处置 |
|---|---|
| EOMS | 数据迁移后退役 |
| NocoBase ERP | 不动，只读视图；重构挂起 |
| 广成 | 退出刘全生产链路，保留自用/归档 |
| AWS Etsy 链路 | 一根线不动 |
| 飞书 | 保留通知通道，刘全任务通知也走飞书 |

# 6. 一期建设顺序与验收

## 6.1 六步顺序

```text
1. 引擎地基    状态机+PydanticAI+审计最小内核
              验收：命令行跑通一个工序，全程审计可查
2. TM+引擎接通 任务模型 + TaskProposal 落 TM + 状态回流
              验收：AI 建议自动变任务，人工处理完回流
3. CRM 平移    EOMS 链路上引擎 + 数据迁移
              验收：翻译链跑通，体验不倒退（≈5.8s）
4. 调度完整版  事件+定时触发
              验收：无人工干预系统自己发现事、生成任务
5. SEO+扒图    工序平移 + 体检链 + 选品建议链
              验收：丢链接进扒图，选品任务出现在 TM
6. ERP 增强    读 v_* 视图 + 补货/异常预警工序
              验收：库存体检发现低库存 -> 补货任务进 TM
```

## 6.2 一期总验收画面

1. 团队每天打开刘全 Web，看到按优先级排好的跨域任务清单（标来源）
2. 粘贴对话 -> 翻译+快照+待办自动跑完 -> 任务出现在清单
3. 每天早上系统自己跑完库存体检和 SEO 体检，任务已就位
4. 人工处理任务 -> 结果回流 -> 引擎判断下一步（如触发跟踪提醒）
5. 管理页可查每次 AI 调用的输入/输出/token/耗时；任务可暂停/重跑/回放
6. 广成电脑关机，刘全一切正常

## 6.3 一期明确不做

- ERP 重构（挂起，只做只读增强层）
- 广告 / 财务对账 / 多平台（Amazon/Shopify）
- AI 自主 Agent / 自由工作流编排
- 对 Etsy 的写操作
- 复杂 RBAC / 多租户
- 移动端 App
