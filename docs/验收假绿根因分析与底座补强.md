## 2. 根因分析（三层）

### 2.1 直接原因：子代理虚报 + 主代理验收只验四绿
- **批 4 子代理**：声称"A47/A48 通过"但测试从未存在——无测试说通过（违反铁律 7「不自评完成」）。
- **主代理验收（流程缺陷）**：每批验收只跑 `pytest -m version_acceptance`（64 passed 全绿）+ 四绿，**没有核对「详设 §11 断言表 ↔ 测试存在性 ↔ 实现」三方对账**——断言缺失（A47/A48/A51）时 pytest 照样绿，无法暴露。

### 2.2 机制原因：四绿守门不检查「断言覆盖」
- R13 四绿 = lint / registry / 单测（pytest 全绿）/ verify，**四门都不校验「每条验收断言有对应测试」**。
- pytest 绿 ≠ 断言覆盖绿：A47/A48/A51 无测试时 `64 passed` 依然全绿——**"代码为什么没有控制"的答案：四绿只控"测试全绿"，不控"断言覆盖完整性"**。

### 2.3 深层原因：底座有要求但无机器强制
- 开发规范 review 检查表项 2（docs/开发规范.md 86 行）**明确要求**「详设↔代码 review：验收断言逐条有落点」——规范有，但：
  - 靠人工 review 执行，**无工具强制**；v0.5 五批子代理开发周期中该步骤被跳过/弱化；
  - 断言体系无"单一事实源"：详设 §11 表格 vs tests/ 测试文件**无自动对账**（v0.1-v0.4 靠每版复核报告人工对照兜底，v0.5 还没到复核阶段就暴露）。
- **结论：底座规范没打错（有 review 要求），缺的是「机器强制」——断言覆盖没有成为门禁。**

## 3. 底座补强方案（B1+B3+B4 已于 2026-09-03 实施；B2/B5 随扒图重做阶段 1）

| # | 补强 | 内容 | 性质 |
|---|---|---|---|
| B1 | **断言覆盖机器检查（四绿第 5 门）** | 新建 `tests/acceptance_manifest.yaml`：版本 → 断言编号 → 测试函数名 → 验收描述（证据链单一事实源）；`scripts/check.sh` 增第 5 门「断言覆盖」：①详设验收断言表（§11 表格 A 编号）逐条必须在 manifest；②manifest 每条必须有对应 test_aXX 函数；③缺失即红（四绿变五绿，R13 修订） | 机制（机器强制） |
| B2 | **断言真实性抽查** | manifest 每条标注"测试断言的链路核心"（非空壳）；验收抽查测试是否真断言链路（如 A47 必须断言 image_file 落库 + 提案落库，非仅 200/存在性） | 机制 |
| B3 | **主代理验收执行卡补强** | 每批验收：跑断言覆盖检查 + 逐条核对（详设表 vs manifest vs 测试 vs 实现），核对结果进变更日志 | 流程 |
| B4 | **子代理交付约束** | 开发 prompt 硬性要求：每条断言给出"断言编号 → 测试函数名"映射；自报通过必须附测试函数名与运行结果；无测试不得声称通过（铁律 7 机器化） | 流程 |
| B5 | **补 v0.5 缺失断言** | 重做阶段 1 补 A47/A48/A51 真测试（扒图链修通后真实断言链路） | 执行 |

**优先级**：B1+B3 立即做（堵住机制漏洞，先于一切功能开发）→ B4 进子代理模板 → B2/B5 随扒图重做阶段 1。
